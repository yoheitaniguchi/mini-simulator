## 3. ドメインロジックの実装方針（設計メモ）

### 3.1 型設計のポイント

- `Order.status` はサマリー用の粗い状態（受注済／引当中／出荷済／取消済）。
  §3の状態遷移図の通り、BOMのどの階層であっても最初にWIP（仕掛）が1つでも開始された時点で
  `受注済 → 引当中` に遷移させる（§9-1 D4「制御盤の引当成立→仕掛開始」の時点で受注ステータスが
  変わっている記述に合わせた）。
- 仕掛品・完成品在庫は「受注ごと・品目ごとに1レコード、二値判定」（§4, §16）。数量は持たない。
  受注数量はBOM展開時の所要数計算（購買品の必要数）にのみ影響し、内製品のWIP/FGレコードは
  受注数量に関わらず1件のみ（＝その受注に必要な数量をまとめた1ロットとして扱う）。
- 材料の有効在庫（§4）は「現在庫 − 引当済数量」だが、本設計は仕掛開始時に材料を一括消費する
  （§4本文、CLAUDE.mdの差分メモにも記載）ため、消費前の「引当済だが未消費」という中間状態は
  存在しない。したがって実装上は「現在庫がそのまま有効在庫」として扱ってよい（引当済数量は常に0）。

### 3.2 関数構成（`src/domain/logic.ts`）

CLAUDE.mdが名指ししている関数名 `attemptAllocate` / `computeRequiredTree` を踏襲する。

- `computeRequiredTree(state, order, itemId, multiplier)`
  BOMを再帰的に辿り、その受注についてまだ消費されていない（WIP/FGレコードが無い）購買品の
  必要数量を集計するマップを返す。§5の二重発注防止判定（「未充足の全受注の所要数合計」）の算出に使う。
- `attemptAllocate(state, order, itemId, multiplier, day, log)`
  内製品ノードを再帰的に辿り、直下の構成品（購買品は在庫、内製品はFGレコードの有無）が揃っていれば
  仕掛開始（WIPレコード作成・構成品消費）する。揃っていなければ、購買品側は調達への発注要求
  （§5の判定式）を、内製品側はさらに下位への再帰呼び出しを行う。
- `checkAndPlaceProcurement(state, itemId, day, log)`
  §5の発注要否判定式（有効在庫＋発注残 ≥ 未充足の全受注の所要数合計）を評価し、不足分のみ発注する。
- `advanceDay(state, log)`
  §8の1日の処理順序（入荷判定→仕掛完成判定→新規引当試行→出荷判定）を固定順で実行する。
- `createOrder(state, input)` / `cancelOrder(state, orderId)`
  受注登録・取消（§7）。

すべて「呼び出し側が渡した状態を直接書き換える」設計とし（CLAUDE.md記載の方針通り）、
`reducer.ts` 側で `structuredClone` してから渡す。

### 3.3 テスト方針

`docs/design.md` §9-1（クリティカルパス演習）・§9-2（優先順位ルール演習）の日次テーブルを、
そのまま自動テスト（vitest）として実装する。具体的には、各Dayまで `advanceDay` を実行し、
その時点での受注ステータス・WIP/FG・在庫・発注残が設計書の記述と一致することをアサートする。
加えて、取消ロジック（§7）・二重発注防止（§5）の単体テストも追加する。
